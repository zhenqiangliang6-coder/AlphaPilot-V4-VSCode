一、首先，把你的所有想法统一成一个核心循环
你提出的：
capability_missing → 反思 → 检索 → 生成 → 沙盒验证 → 入库
这是非常重要的设计。
我建议把它正式定义为：
Capability Evolution Loop（能力进化循环）
Task Execution — 执行用户任务，调用已有工具和 Agent
Capability Detection — capability_missing，发现工具不存在、能力不足或执行失败
Reflection Engine — 我缺什么？有没有可复用能力？是否需要新建？
Capability Discovery — 搜索已有工具、技能、文档和模板
Skill Generation — 生成候选工具及其契约和测试
Sandbox Validation — 隔离执行、测试、审计、验证
Human Approval & Registry — 审核通过、版本化注册、可回滚
新能力进入下一轮任务执行。
1.1 工具唯一性原则（Tool Uniqueness）
这里有一个关键的设计约束，必须写进核心规则里：
在创造新 Skill 之前，必须优先考虑工具唯一性。
这个原则来源于 Voyager 的思路：每学会一个新能力就写成代码存进 Skill Library，下次先检索，找不到再创造新的。但更重要的是——不要重复创造已有能力覆盖范围内的功能。
例如：Alphapilot 要创建一个 Java Skill，但发现很多 Python 在用的 Skill 的一些步骤流程就可以复用。如果它再重复创造，就不符合工具唯一性。它只需要创造没有的那部分差异。
具体规则：
先查库：遇到 Java、Go、数据库迁移、前端构建这类需求，先问自己：“我现有的 Python/Node/Java 工具链里，有没有能复用的步骤？”
再做唯一性判断：不要一上来就新建一个 Java Skill。环境检测逻辑可以复用；版本校验流程可以复用；构建产物验证可以复用；但 pip install 不能直接复用，必须换成 mvn/gradle。
只生成差异部分：新 Skill = 已有通用步骤 + 目标语言特有步骤 + 沙盒验证规则，而不是从零重写一整套。
注册前做去重检查：入库前检查是否已有相同触发条件、相同执行路径、是否只是参数不同、是否能被现有 Skill 组合覆盖。
这样 Alphapilot 就不会越跑越臃肿。它不是”每遇到一个新问题就长一个新器官”，而是先复用，再组合，最后才创造。
1.1.1 第五条宪法：Capability = 唯一生产实现
定义：对于同一个规范化 capability_id、相同能力语义及相同作用范围，生产环境中只能存在一个由 Registry 正式管理的权威能力实现入口。这里的“唯一”约束的是生产能力归属与调用入口，不是要求能力内部只能有一种算法或执行策略。
唯一性判定不能只比较函数名、文件名或 Agent 名称。应结合 capability_id、能力语义、输入输出契约、适用范围（runtime / language / environment）及版本状态进行判断，避免同名异义或异名同义造成误判。
允许：
多个 Agent 调用同一个 Capability 入口；调用方不同，不意味着可以各自复制一套实现。
Capability 内部采用多策略、fallback 或链式降级；只要它们由同一个受 Registry 管理的能力入口统一编排，并共享契约、权限和审计边界，就仍属于一个生产实现。
能力实现可以升级或替换；新实现通过兼容性与回归验证后接管同一能力入口，旧版本按迁移策略退役。必要的灰度/回滚版本属于受控发布过程，不构成多个独立能力实现。
不允许：
Agent 私自构建同类能力链条，例如自行拼接 prompt → LLM → parse，绕过已注册的 Capability。
Agent Fork 已有能力并将复制修改版作为并行生产实现长期运行。
Agent 复制 Prompt 工程、解析规则或模板，绕过统一 PromptBuilder / 标准模板及版本管理。
Agent 绕过标准能力执行入口，直接调用内部实现或跳过 Contract、Permission Guard、必要的 Verifier 与执行审计。
工程落地：CapabilityRegistry 负责唯一性约束和版本状态；CapabilityResolver 负责查找与选择权威入口；统一执行网关（例如 execute_step）负责契约校验、权限检查、调用、验证和证据记录。Agent 只能通过网关调用能力，不能直接访问生产实现内部细节。
补充边界：实验分支、候选生成物和沙盒中的临时实现可以并存，但它们必须标记为 candidate / sandbox / deprecated 等非生产状态，不能绕过验证和审批进入正式调用路径。
1.1.2 第六条规则：Agent 不允许发明能力，只能申请能力
Agent 可以识别能力缺口、提交 CapabilityRequest、说明任务目标与输入输出要求、提供失败证据，并提出复用、扩展或新建建议；但 Agent 本身无权直接创建、复制、注册或发布新的生产 Capability。
能力是否需要新增，由 ReflectionEngine 基于现有 Registry、能力语义、执行证据和兼容性分析作出结构化决策；候选实现由受控生成流程创建，在 SandboxRunner 中验证，并经过相应审批策略后，才由 Registry 注册或升级。
因此，Agent 的职责是“申请与提议”，平台的职责是“判断、生成、验证、授权和注册”。这条规则将能力进化权从单个 Agent 收回到 Agent OS 的统一治理层。
1.2 执行失败不等于能力缺失
这里我想纠正一个可能产生问题的地方：
执行失败，不一定代表能力缺失。
失败情况
应该怎么处理
没有 Java 工具
capability_missing
Java 工具存在，但 JDK 未安装

Maven 下载超时

这些状态不能全部归为 capability_missing。
否则 Alphapilot 可能遇到一次网络超时，就错误地开始创造一个新工具。
我建议建立统一的事件分类体系，并在 Reflection Engine 的输入中结构化传递这些分类信息。

2.1 HumanApproval 环节的落地优化
方向是对的，但实际落地时需要考虑：如果 Alphapilot 日常运行中频繁触发能力创建流程，人类审批会成为巨大的吞吐量瓶颈。建议区分高风险能力（需要人工审批）和低风险能力（沙盒验证通过即自动注册，但带可回滚标记）。比如检测 Python 环境这种低风险操作可以自动入库，而涉及系统权限变更的操作才需要人工审批。

我认为这是你目前架构中最需要明确的概念边界。
这四个东西不能混为一谈。

我建议你把 Capability Registry 设计成整个 Alphapilot 的能力中心，而 Tool Registry 只是它的底层执行注册表。
3.1 Registry 应该具有唯一性和版本管理
例如：
{  "capability_id": "rust_project_setup",  "version": "1.0.0",  "owner": "rust_env_agent",  "skill": "rust_project_setup",  "tools": ["detect_rust", "cargo_init", "cargo_build"],  "status": "active",  "verified": true,  "evidence_id": "ev_001"}
还需要考虑：
同一个能力不能因为不同 Agent 注册而重复。
新版本不能直接覆盖正在使用的旧版本。
能力升级必须经过兼容性测试。
失败的候选工具不能进入正式 Registry。
已有能力需要支持禁用和回滚。
这里的唯一性建议基于规范化的 capability_id、能力语义和版本约束，而不是简单比较名称。
进一步明确：对同一规范化 capability_id 与作用范围，Registry 应保证只有一个 active 的权威生产入口。多个版本可以作为候选、灰度或回滚版本存在，但必须由同一发布/路由策略治理，不能让 Agent 各自维护互不受控的生产分叉。
Agent 申请新能力时，应提交 CapabilityRequest（目标、场景、输入输出契约、失败分类、证据及期望范围）；Registry 不接受 Agent 直接写入生产记录。候选能力必须经过语义去重、契约检查、沙盒验证、兼容性测试和审批策略。

3.2 CapabilityResolver 评分与路由策略
CapabilityResolver 不仅负责查找能力，还负责在多个候选能力中做出最优选择。当多个 Capability 都能完成同一任务时，需要一套明确的评分与路由策略来决定优先级。
评分维度：
语义匹配度：能力描述与任务需求的相似度评分，基于能力声明的 input_schema、output_schema 和描述文本进行向量匹配或关键词匹配。匹配度低于阈值的候选直接排除。
版本新鲜度：优先选择最新稳定版（stable tag），候选版（candidate）和灰度版（canary）降级处理。已弃用（deprecated）版本不参与路由。
历史成功率：基于沙盒验证通过率和运行时成功率进行加权评分。连续失败次数超过阈值的Capability自动降级为熔断状态。
资源消耗基线：优先选择轻量级实现。对于计算密集型任务，优先路由到资源消耗低的Capability。
路由策略：
首选策略：按评分排序，选择最高分且状态为 active 的Capability。
降级策略：首选不可用时，按评分降级到候选版本或备用Capability。
熔断策略：当某Capability连续失败次数超过阈值（默认5次），自动熔断60秒，期间请求路由到备用能力或返回结构化错误。
熔断恢复：熔断期满后自动半开状态，放行一次探测请求。成功则恢复，失败则重新熔断并告警。

3.3 能力退役策略（Capability Retirement）
文档讲了能力创建和升级，但能力退役同样重要。一个健康的能力库不仅需要好的"出生"机制，还需要好的"退休"机制。未经治理的能力退役会导致：废弃能力继续被调用产生错误、依赖关系断裂、文档与实际不一致。
能力退役三阶段（已在 5.9.4 提及，此处细化）：
第一阶段 - 标记弃用（Deprecated）：在 CapabilityRegistry 中将能力状态标记为 deprecated，同时设置弃用日期。所有新请求禁止路由到该能力，但已有任务可继续完成。在 API 响应头中返回 Deprecation 警告字段。
第二阶段 - 告警过渡（Warning）：在弃用日期过后进入过渡期（建议 30 天）。调用该能力的请求返回结构化警告，包含替代能力推荐和迁移指南。监控该能力的调用量，评估影响范围。
第三阶段 - 正式移除（Removal）：过渡期结束后正式移除能力。移除前检查所有依赖项（通过能力依赖图分析），确保没有活跃依赖。移除后保留归档记录（含版本快照和迁移文档）至少一个主版本周期。
退役前依赖检查清单：
扫描 CapabilityRegistry 中所有 active 能力的依赖图，确认无其他能力依赖被退役能力；
检查 AgentContract 中是否有 Agent 声明依赖该能力；
检查 CI/CD 流水线、文档、示例代码中是否有硬编码引用；
通知所有相关 Agent 所有者和团队成员。
灰度退役方案：
对于影响范围较大的能力退役，建议采用双写过渡期：新旧能力并行运行一段时间，新请求路由到新能力，旧能力仅用于兼容性验证。过渡期结束后关闭旧能力，观察无异常后归档。

注意一个细节：

A2A 也不仅仅是简单的 Agent 间消息传递，它涉及 Agent 能力发现、任务生命周期和任务结果交付。
我建议不要现在就为了使用协议而实现所有协议。
先让内部 Agent 之间通过稳定的 Python 接口和 Pydantic 契约协作，等需要跨进程、跨机器或连接第三方 Agent 时，再引入 MCP/A2A 的协议适配层。
这样不会过早增加系统复杂度。

五、多 Agent 协作的契约层设计（新增）
这是 Alphapilot 从”单 Agent 工具集”走向”多 Agent 工程执行系统”的关键基础设施。
5.1 契约层要管住的不是”聊天”，而是三件事
每个 Agent 能做什么
它接收什么、必须返回什么
它失败、越权、版本不兼容时怎么处理
契约层一旦失控，新增 Agent 就会出现三种典型问题：协议错乱、职责重叠、状态被覆盖。
5.2 先给契约层划清边界
可以把契约层拆成四层，新增 Agent 只能按这四层接入：
层
管什么
新增 Agent 能改什么
角色契约
职责、边界、禁止项
只能声明自己的角色，不能改别人
数据契约
输入输出 Schema
只能按已有 Schema 收发
版本契约
协议版本、兼容规则
必须带版本号，不能静默改字段
生命周期契约
超时、重试、熔断、回滚
必须遵守统一失败路径
这样扩展就不会变成”每个新 Agent 都带一套自己的规矩”。
5.3 角色契约：防止新增 Agent 抢活或越权
每个 Agent 注册时必须声明：
{  "agent_id": "java_env_agent",  "role": "executor",  "scope_in": ["detect_java", "mvn_build", "verify_build"],  "scope_out": ["write_plan", "approve_release", "modify_other_agent_state"],  "allowed_tools": ["shell", "file_read", "file_write"],  "escalation": "return blocker + tried_steps"}
这里最关键的是 Scope-Out：明确写出它绝对不能做的事。
比如 Coder 不能改 Planner 的计划，Reviewer 不能重写需求，Verifier 不能没有证据就放行。
5.4 数据契约：新增 Agent 不能随意改消息格式
所有 Agent 间通信必须走统一信封：
{  "msg_id": "m_001",  "trace_id": "t_abc",  "version": "a2a.v1",  "from": "planner",  "to": "coder",  "task_id": "task_12",  "type": "task_handoff",  "payload": {},  "ttl": 30,  "timestamp": 1730419200}
新增 Agent 时遵守三条规则：
不能删已有字段；
不能改字段语义；
新增字段必须是可选的，并带默认值。
如果某个 Agent 需要新字段，应该走”扩展字段 + 版本升级”，而不是直接改旧协议。
5.5 版本契约：避免新旧 Agent 互相听不懂
每个契约和消息都要带版本号。可以采用类似语义化版本：
v1.0 → v1.1：只允许新增可选字段；
v1.x → v2.0：允许破坏性变更，但必须通过适配器；
跨主版本不直接混跑，除非有兼容层。
比如新 Agent 想加一个 confidence 字段，可以放在 v1.1 里；但如果它要把原来的 files 改成 file_changes，就必须升到 v2，并提供适配器，把旧格式转成新格式。
5.6 能力注册 + 唯一性检查：防止重复 Agent 造成冲突
这里接上前面说的”工具唯一性”。
新增 Agent 注册时，先跑一次检查：
新 Agent 能力 ∩ 已有能力 ≠ 空集？→ 是：判断是复用、组合，还是冲突→ 否：允许注册
例如新增一个 go_build_agent，系统发现：
detect_runtime 已有；
verify_build_output 已有；
只有 go mod tidy、go build 是新的。
那它就不应该重建整套流程，只注册差异部分。这样 Alphapilot 的能力库会越来越轻，而不是越堆越乱。
5.7 状态隔离：防止新 Agent 改坏全局状态
多 Agent 最容易乱的地方不是”发消息”，而是共享状态被覆盖。
规则可以定死：
每个任务有独立 task_state；
Agent 不能直接改全局状态；
写文件前必须声明目标文件和预期版本；
提交时检查文件是否已被其他 Agent 修改；
所有状态变更必须带 trace_id 和 task_id。
这样即使新增一个 Agent，它也只能在自己的任务快照里工作，不会偷偷污染别的 Agent。
5.8 冲突仲裁：谁说了算要提前写进契约
冲突通常有三种：
职责冲突：两个 Agent 都想处理同一件事；
资源冲突：两个 Agent 同时写同一个文件；
结论冲突：Coder 说完成，Verifier 说不通过。
处理方式可以统一成：
职责冲突 → 交给 Orchestrator 按角色契约路由；
资源冲突 → 文件锁 + 版本校验；
结论冲突 → Verifier 有更高优先级，但必须返回证据；
无法仲裁 → 升级给人或 Planner 重规划。
5.9 契约层的演进设计：让协议随系统升级自动兼容
契约层要能演进，关键不是”永远不改”，而是改的时候有规则、有版本、有适配、有观测。
5.9.1 分层策略：核心协议不变，扩展协议可长
层
管什么
演进规则
核心协议
msg_id、trace_id、task_id、version、from、to、type
极少改动，必须强兼容
能力契约
Agent 能做什么、输入输出 Schema
可新增能力，但旧能力不能静默删除
扩展协议
新字段、新技能、新 RPC

这样 Alphapilot 升级时，核心信封不动，新增能力走扩展层，不会把旧 Agent 直接搞崩。
5.9.2 Schema 规则：新增字段必须可选，删除字段必须弃用
新增 Agent 时遵守三条硬规则：
不能删已有必填字段；
不能改已有字段语义；
新增字段必须是可选的，并有默认行为。
比如原来只有：
{"files": ["schema.sql"]}
新版本想加置信度，可以这样扩：
{"files": ["schema.sql"], "confidence": 0.92, "explanation": "已通过沙盒验证"}
旧 Agent 没有 confidence 也能继续跑；新 Agent 收到旧消息时，把缺失字段当成默认值处理。
5.9.3 自动兼容：协商 + 能力探测 + 适配器
Alphapilot 升级后，可以按这个流程自动对齐：
1. 读取对方 AgentCard2. 检查 protocol_version 是否兼容3. 检查所需能力是否存在4. 如果字段缺失，使用默认值5. 如果主版本不同，走适配器6. 如果无法兼容，降级或拒绝
5.9.4 弃用管理：删除字段必须经过三阶段
v1.3：标记 deprecatedv1.4：继续支持但告警v2.0：正式移除，并提供迁移脚本
5.9.5 新增 Agent 的准入流程
1. 声明角色契约2. 声明输入输出 Schema3. 声明协议版本4. 做能力唯一性检查5. 做状态访问范围检查6. 跑沙盒验证7. 通过后注册进能力表8. 失败则拒绝上线
只要有一条不通过，就不允许进入系统。这样扩展就不是”随便加一个 Agent”，而是”通过契约审查后接入一个能力节点”。

六、你提出的 State Snapshot：这是 Multi-Agent 最关键的基础
我非常赞同你提出的：
状态不能靠聊天传递。
这句话我认为可以成为 Alphapilot 的架构原则之一。
但是，我建议把 State Snapshot 设计得比普通 JSON 更完整。
它应该包含：
当前任务目标。
已确定的决策。
当前执行状态。
已产生的文件和资源。
未完成任务。
依赖关系。
风险和限制。
版本及恢复锚点。
6.1 推荐的数据结构
下面是一个可以直接发展成 Pydantic v2 模型的初版：

这里我建议再做两个调整：
实际生产代码中使用 Field(default_factory=list)，避免可变默认值。
state_version 应当有独立的版本演进规则，不能简单认为它就是整个项目的版本。
6.2 一个容易忽略的问题：Snapshot 不应该是唯一事实来源
例如：
Coder Agent 创建了 backend/main.py。
Reviewer Agent 修改了它。
如果 Planner 仍然持有旧 Snapshot，就可能覆盖 Reviewer 的修改。
所以我建议：
Snapshot 负责描述状态，Event Log 负责记录状态变化。
例如：
TASK_CREATEDPROJECT_SPEC_APPROVEDFILE_CREATEDCODE_GENERATEDCODE_REVIEWEDFILE_MODIFIEDTASK_COMPLETED
每个事件都有：
{  "event_id": "evt_001",  "task_id": "task_001",  "trace_id": "trace_001",  "agent_id": "coder_agent",  "event_type": "FILE_CREATED",  "timestamp": "...",  "payload": {}}
这样即使 Agent 崩溃，也可以通过 Snapshot 和事件日志恢复。
我建议采用：
Snapshot：当前状态快照。
Event Log：状态变化记录。
Artifact Store：代码、文件和构建产物。
Task Store：任务生命周期。
这四者不要混在一个 JSON 文件中。

七、你提出的冲突仲裁，我想再修正三个地方
你的思路已经涉及多 Agent 系统中的并发控制了。
但有三个地方值得注意。
7.1 文件锁：建议优先采用乐观并发控制
你的原方案是：
同一文件同一时间只允许一个 Agent 写入。
这可以实现，但如果大量文件都需要锁，调度会越来越复杂。
我更建议：
Agent 读取文件    ↓记录文件版本 / Hash    ↓Agent 修改文件    ↓提交修改    ↓检查原始版本是否变化    |    +-- 没变化 → 接受修改    |    +-- 已变化 → 触发冲突处理
这叫 Optimistic Concurrency Control。
对于确实不能并发修改的资源，再使用有租约和超时机制的锁。
补充：乐观并发的降级策略
当冲突频率超过某个阈值时（说明多个 Agent 在频繁修改同一批文件），应该自动降级为悲观锁（写锁），避免大量重试浪费算力。这个阈值策略需要纳入设计。
具体阈值建议如下：
冲突率 > 10% 持续 5 分钟 → 自动降级为悲观锁（写锁），所有后续写入请求排队等待。降级期间记录告警日志并通知运维。
冲突率回落到 < 5% 持续 10 分钟 → 自动恢复乐观模式，释放所有排队锁。恢复后记录恢复日志。
单次写入超时 > 30 秒 → 放弃当前写入，触发重试（最多3次），重试全部失败则降级为悲观锁并告警。
以上阈值应配置化（而非硬编码），允许不同项目通过 ProjectSpec 的 constraints 字段覆盖默认值。
7.2 Agent 优先级：不要仅靠角色决定谁覆盖谁
你提出：
Planner > Verifier > Coder
我不建议直接使用这种固定优先级。
例如，Verifier 发现 Coder 的代码存在问题，应该有权阻止合并；但不意味着 Verifier 可以随意覆盖代码。
更好的做法是：
角色
权限
Planner
修改任务计划
Coder
提交代码修改
Reviewer
审核和提出修改意见
Verifier
执行测试、判定是否通过
Orchestrator
决定任务状态和合并流程
职责权限和执行优先级是两个不同的概念。
7.3 死锁预防：DAG 只是第一道防线
你说不允许循环依赖，这非常正确。
但还应该补充：
Agent 等待必须有超时。
锁必须有 TTL。
任务必须支持取消。
Agent 失联必须有恢复机制。
任务重试必须有次数上限。
外部副作用必须考虑幂等性。
另外，任务 DAG 中的循环依赖可以静态检查，但运行时的资源等待还需要单独监控。
工业上通常优先尝试重规划，其次才回滚或强制释放资源。

八、容器级沙盒隔离设计（新增）
进程级隔离（subprocess）在”执行用户代码”这个场景下太脆弱了——一个精心构造的 fork() 炸弹或者 /dev/null 重定向就能突破边界。
容器级隔离（Docker）是 Alphapilot 走向生产级的必经之路。
8.1 为什么必须上容器
进程级隔离的致命缺陷：
权限逃逸：root 进程可以挂载文件系统、修改 /proc、读取其他进程内存
资源耗尽：ulimit 可以被进程自己改，cgroup 可以被子进程绕过
网络隔离不彻底：network namespace 可以绕过，直接访问宿主机网络
审计困难：进程销毁后痕迹难追溯
容器的优势在于：内核级隔离 + 强制资源限制 + 不可变执行环境 + 完整审计。对 Alphapilot 来说，每个 Skill 执行都在一个临时容器里跑，跑完就销毁，不留痕迹。
8.2 容器沙盒在 Alphapilot 中的位置
Planner  ↓ (task)ExecutionEngine  ↓ (execute_in_sandbox)SandboxManager  ├── DockerDriver (容器执行)  ├── ProcessDriver (进程执行，降级用)  └── MockDriver (测试用)  ↓Result + Trace
关键设计：SandboxManager 是抽象层，不直接依赖 Docker。这样：
开发环境可以用 ProcessDriver 快速迭代
测试环境用 MockDriver
生产环境用 DockerDriver
后续如果要换 containerd / nerdctl，只改 Driver 实现
8.3 容器生命周期设计
每个 Skill 执行对应一个临时容器，生命周期如下：
创建 → 注入代码 → 执行(带超时/资源限制) → 收集结果 → 清理
具体步骤：
创建阶段
从预构建的基础镜像启动（比如 alphapilot/sandbox-base:latest）
基础镜像里预装常见运行时（Python、Node、Java 等），避免每次拉镜像
分配独立网络 namespace（默认 deny all，按需开放）
挂载只读的代码目录 + 只写的输出目录
注入阶段
通过 bind mount 或 docker cp 把待执行代码注入容器
设置环境变量（TASK_ID, TRACE_ID, SANDBOX_ID）
以非 root 用户运行（user: “1000:1000”）
执行阶段
设置 stop_timeout（比如 60s）
通过 cgroup 限制 CPU（–cpus=1）、内存（–memory=512m）、PID（–pids-limit=100）
限制网络：默认 –network none，需要联网的 Skill 才开 bridge 并配防火墙规则
限制磁盘写入：–tmpfs /tmp:size=100m + 输出目录单独挂载
收集阶段
捕获 stdout/stderr
捕获退出码
收集容器指标（CPU/内存峰值、IO 操作）
保存容器日志到 Event Log
清理阶段
docker stop → docker rm
清理临时文件
释放网络资源
8.4 安全设计要点
这是最关键的部分，容器不等于安全，配置不当反而更危险：
8.4.1 镜像安全
基础镜像用 distroless 或 alpine 最小化镜像
镜像签名验证（docker content trust）
定期扫描镜像漏洞（trivy / grype）
禁止从公网拉镜像，所有镜像走内部 registry
8.4.2 运行时安全
禁止 privileged 模式
禁止 –cap-add=ALL，只开必要的 capabilities
禁止 hostNetwork、hostPID、hostIPC
只读根文件系统：–read-only + 需要写的目录用 tmpfs
禁止容器内访问宿主机 socket
8.4.3 网络隔离
默认策略：DENY ALL按需开放：  - 包管理镜像源（pypi/npm/maven）→ 白名单域名  - 数据库连接 → 内网 IP 白名单  - 禁止访问元数据服务（169.254.169.254）
8.4.4 文件系统隔离
代码目录只读挂载
输出目录独立挂载，执行后统一收集
/tmp 用 tmpfs 限制大小
禁止访问 /etc/passwd 以外的系统文件（通过 seccomp Profile）

8.4.5 威胁模型（Threat Model）
容器安全配置再严格，如果不知道"我们在防御什么"，仍然会漏防。建议在第八章中明确定义威胁模型，为后续安全设计提供明确的防御目标。
核心威胁分类：
恶意 Skill 代码：用户提交的 Skill 代码可能是恶意的，包含后门、数据窃取逻辑或破坏性操作。防御措施：沙盒隔离 + 代码审计 + 行为监控。
LLM Prompt Injection：如果 Agent 将用户输入直接拼接到 LLM prompt 中，攻击者可能通过注入指令操控 Agent 行为。防御措施：prompt 参数化 + 输入 sanitization + 输出校验。
供应链攻击：通过 pip install / npm install / mvn 等包管理器引入恶意依赖，污染构建产物。防御措施：依赖白名单 + 镜像签名验证 + 依赖漏洞扫描（trivy/grype）。
数据泄露：Agent 执行过程中可能接触到敏感配置（数据库密码、API Key、SSH 密钥等）。防御措施：环境变量隔离 + 密钥管理服务 + 执行日志脱敏。
资源耗尽攻击：恶意任务消耗所有容器资源（CPU/内存/磁盘/网络），导致服务不可用。防御措施：cgroup 资源限制 + 请求速率限制 + 超时熔断。
权限提升：容器内的进程尝试突破容器边界，获取宿主机权限。防御措施：非 root 用户运行 + 只读文件系统 + seccomp/AppArmor  Profile + 禁止 privileged 模式。
威胁评估矩阵：
每种威胁应按"可能性"和"影响程度"两个维度评估风险等级（高/中/低），并对应不同的缓解优先级。高风险威胁必须在 V0.3 前完成防御实现，中风险在 V0.4 前完成，低风险纳入技术债务 backlog。
8.5 性能优化策略
容器启动慢是最大痛点。几个优化手段：
8.5.1 镜像预热
预构建常用运行时镜像并本地缓存
用 docker pull –all-platforms 提前拉取
8.5.2 容器复用（谨慎使用）
对于轻量级 Skill（如代码格式化、lint），可以复用长驻容器
但必须做状态清理：每次执行前重置工作目录、清空临时文件
复用容器需要更强的隔离保证（更严格的 seccomp + apparmor）
8.5.3 并行执行
DAG 中无依赖的任务可以并行在多个容器里执行
需要控制并发度（max_concurrent_sandboxes），避免资源耗尽
8.5.4 快照恢复
对于频繁创建的基础环境，用容器快照（docker diff + docker export）加速
类似 docker build –cache-from 的思路
8.6 与能力进化循环的集成
容器沙盒不只是”执行环境”，它还是能力验证的基础设施：
新 Skill 生成  ↓沙盒验证（Docker 容器）  ├── 单元测试执行  ├── 集成测试执行  ├── 资源消耗检测（CPU/内存/时间）  ├── 安全扫描（seccomp 违规、网络违规）  ↓通过？ → 入库注册失败？ → 返回错误给 Reflection Engine
这里的关键是：沙盒验证的结果必须结构化，包含：
测试通过率
资源消耗基线
安全合规状态
性能指标（冷启动时间、执行时间）
这些数据可以反馈给 CapabilityResolver，帮助判断：
这个新 Skill 是否值得入库
是否有已有 Skill 可以替代
是否需要拆分或合并

9.2.1 契约测试的具体实现思路
契约测试是保证契约层不被破坏的第一道防线。由于 Alphapilot 的契约层是整个系统协作的基础，任何契约的破坏都可能导致多 Agent 协作链路断裂。
实现方案：
每个 Contract（AgentContract / ToolContract / CapabilityContract）都必须有对应的 JSON Schema 测试用例。使用 Pydantic v2 的 model_json_schema() 方法自动生成 JSON Schema，然后与手写或历史版本进行 diff 比较。
每次协议版本升级（如 a2a.v1 → a2a.v2）必须跑契约兼容性测试：前向兼容性（新客户端能否读取旧服务端数据）和后向兼容性（旧客户端能否读取新服务端数据）。不兼容的变更必须在变更说明中明确标注破坏性。
可以使用 pytest-jsonschema 或 pydantic 的 TypeAdapter 进行运行时 Schema 校验，在 CI/CD 流水线中自动拦截不合规的契约变更。
契约测试应覆盖以下场景：
必填字段缺失时校验失败；
字段类型不匹配时校验失败；
新增可选字段不影响旧客户端；
删除必填字段时测试失败（阻止破坏性变更）；
枚举值超范围时校验失败。

9.3 模型路由策略（Model Router）
文档提到了 Model Router 作为横向基础设施，但 Agent 系统通常需要多种模型协同工作：简单任务用小模型（快、便宜），复杂规划用大模型（质量好），代码生成用专用代码模型。需要一个路由策略来决定每个步骤用哪个模型。
路由决策维度：
任务复杂度：根据 Task Decomposer 对任务的分析结果，简单任务（如文件读取、格式检查）路由到轻量模型，复杂任务（如架构设计、多步推理）路由到强推理模型。
任务类型：代码生成任务路由到代码专用模型（如 Codex、StarCoder），自然语言任务路由到通用语言模型，数学/逻辑任务路由到推理增强模型。
成本预算：每个任务分配 token 预算，超预算时自动降级到更便宜的模型或触发截断策略。
延迟要求：用户交互场景（如 IDE 插件）要求低延迟，路由到快速模型；批处理场景可路由到高质量模型。
路由策略实现：
在 ExecutionEngine 中集成 ModelRouter 组件，每个需要 LLM 调用的步骤先经过路由器决策。路由器维护一个模型注册表（ModelRegistry），记录各模型的 capabilities、latency、cost、quality_score 等元数据。
支持 fallback 链：主模型不可用时自动降级到备用模型。降级时标记响应质量可能受影响，供下游组件感知。
收集各模型的调用统计（延迟、成功率、token 消耗），定期更新路由权重，实现自适应路由优化。

十二、架构决策记录（ADR）机制
文档本身是架构决策的集合，但没有说明"未来的架构决策怎么管"。随着 Alphapilot 持续演进，会有越来越多的架构决策产生。如果没有规范的记录机制，这些决策会逐渐散落在代码注释、聊天记录和邮件中，最终导致团队对架构理解不一致。
ADR（Architecture Decision Record）是一种轻量级的架构决策记录格式，核心思想是：每次重大架构变更写一份 ADR，记录决策的背景、决策内容、后果和当前状态。
ADR 模板：
标题：简短描述决策主题（如"采用 Docker 容器作为沙盒执行环境"）。
背景：为什么需要做这个决策？当前面临什么问题？有哪些替代方案？
决策：我们选择了什么方案？为什么选它？
后果：这个决策的利弊是什么？哪些地方会受影响？
状态：accepted（已接受）/ proposed（提议中）/ superseded（已被替代）/ deprecated（已弃用）。
ADR 存放位置：
所有 ADR 文件存放在 docs/adr/ 目录下，按序号命名（如 001-adopt-docker-sandbox.md）。每个 ADR 文件使用 Markdown 格式，便于版本控制和代码审查。
ADR 回顾机制：
每次版本发布前，维护者应回顾 docs/adr/ 目录中状态为 proposed 的 ADR，决定是否提升为 accepted 或标记为 superseded。
过时的 ADR 应标记为 deprecated 并说明替代方案。重大 ADR 的变更应通过 Pull Request 进行代码审查，确保团队共识。
与能力退役策略的关联：
当某个 Capability 需要退役时，应首先创建一份 ADR 记录退役原因、影响范围和迁移计划。退役 ADR 的状态从 accepted 变为 deprecated，经过灰度过渡期后最终标记为 superseded。这确保了能力退役不是悄无声息地发生，而是有完整的决策记录和可追溯性。
