## G10.52 — ModelScope 恢复 200 后非流式长 prompt 卡死（真正根因）

- 突破性诊断：前台单跑 R5 → `1 passed in 82s`（代码正常）；v55 前台单遍
  R5 ✅(195s)/R6 ✅(170s) 后卡在 **R7 fix_code**，worker 停在
  `✅ write_step 生成 1 FileOp` 后的**非流式** `[ModelScope] 调用模型:`，
  三路日志齐停、rc=127。
- 根因：`qwen_client.call()` 早改走 `call_stream` 拼接并带首正文 45s/全程
  240s 墙钟（G10.36）；而 `modelscope_client.call()` 走非流式 `_call_one`，
  只有 requests read timeout(180s)——服务端「连接活跃但持续吐 reasoning/
  保活字节、无完整 body」时 read timeout 永不触发 → hang 死任务链。
  v45 靠 429 被动降级到 qwen_client（有墙钟）才幸免；ModelScope 恢复
  200 后成为唯一无墙钟治理路径，长 prompt（refine/fix 带整个工作区源码）
  偶发卡死。
- 修复（纯生产侧、FAIL-CLOSED）：`modelscope_client.py`
  - 新增墙钟读取函数，复用 `QWEN_STREAM_WALL_TIMEOUT_SEC`=240 /
    `QWEN_STREAM_FIRST_CONTENT_SEC`=45 同口径环境变量；
  - `_stream_one` iter_lines 循环加 monotonic 墙钟，超首正文/全程上界抛
    TimeoutError → 走既有降级链 → `call_llm` 兜底 DashScope；
  - `call()` 改走 `call_stream` 拼接（共用 `_post` 的 429 key 轮换/代理
    路径语义不变），并兼容 json-only 响应（保住旧 key 轮换契约）。
  - 新增 `test_g1052_modelscope_wall_timeout.py`（4 用例）。
- 验证：G10.52 契约 4 passed；provider 相关契约集 83 passed（含旧
  key_rotation/provider_circuit/stream_encoding）；py_compile OK。
